# vm-sync 下一步开发方向（Roadmap）

> 本文记录经评估后的开发方向建议：每条含背景、收益评估、工程注意点与实施边界。
> 已驳回的方向同样记录，避免重复论证。

## 1. Native 格式支持（建议实施，下一阶段首选）

**方向**：导出用 `/api/v1/export?format=native`，导入用 `/api/v1/import?format=native`。
Native 格式保留 VM 内部 Block 结构（长度前缀二进制块流），跳过 JSON 序列化/反序列化。

**收益评估**

| 维度 | 评估 |
|---|---|
| CPU | **主要收益**：大回填时 JSON 编解码是显著开销，native 块直达存储层，两端 CPU 明显下降 |
| 体积 | 原生块本身比 JSON 小得多；但**注意折扣**——链路帧层已有 zstd，而 native 块内部已是 zstd 压缩，二次压缩收益小，链路净带宽收益约 1.2~2×（远小于裸格式的 5~10×） |
| 语义 | "零转换透传"更强：源端不序列化、目标端不解析 |
| 附带收益 | native 块头自带时间戳范围，接收端 e2e 延迟指标（LastSampleTimestamp）从解析 JSON 尾部变为读块头，更便宜 |

**工程注意点（实施边界）**

1. **分块逻辑重写**：现 splitFrames 按"行数+字节"分块（单行不拆）。native 非行式格式，
   必须按块边界拆分（解析长度前缀，整块不拆），`frame_lines` 阈值语义消失（仅字节阈值）。
   切错边界会导致目标端 import 失败。
2. **版本约束**：native 格式随 VM 版本演进。本项目两端同包部署（同一 fork/同版本安装包），
   满足条件；混版本/异构环境必须回退 JSON。因此做成可配置项而非直接替换：
   `export_format: json|native`（默认 json 保兼容，同版本部署切 native）。
3. **可观测性**：JSON 行可人读（DLQ 排查、e2e 假 VM 目标解析 JSON 行断言）。native 落 DLQ
   为二进制，需配套解码工具；e2e 测试需按块解析重写断言。
4. **帧压缩策略**：native 数据帧上 zstd 收益小，可评估"native 帧跳过二次压缩"或按格式
   开关压缩（保留 CRC 与帧结构不变）。

**落地步骤建议**：① 调研 VM export native 流的精确块布局与 import 侧要求 →
② vm 客户端加 `format` 参数与块边界分块 → ③ e2e 往返逐位一致测试（native 路径）→
④ DLQ 解码工具 + 文档 → ⑤ 性能对比（JSON vs native 回填吞吐/CPU）入 docs/performance.md。

## 2. FEC 前向纠错（已驳回，除非拓扑改变）

**结论**：当前架构不适用。当前链路是**正向隔离装置 TCP 映射 + 响应单字节**——
存在反向通道，可靠性由 ACK 驱动（停等/滑窗、WAL 按 ACK 推进、go-back-N 重传）；
TCP 本身已完成丢包修复。在 TCP 之上叠 Reed-Solomon 属双重保险浪费，且 ISFP 是
TCP 流式帧协议，无 UDP 报文层可挂 FEC。

**重新立项条件**：若未来拓扑换成**纯单向数据二极管（无任何反向字节）**，那时才需要
FEC——但那不是"加参数"的改动，而是推翻整个可靠性模型：无 ACK 则 WAL 推进、
last_seq 去重、DLQ 欺骗 ACK 全部失效，At-Least-Once 不成立（发送端无法确认对端
收到），只能退化为"尽力而为 + FEC 概率补偿"。另注意 5~10% 冗余只对偶发小丢包有效，
二极管整段丢弃的故障模式下冗余会被同批吞掉。

**结论**：列为本项目明确不做项（现有拓扑）；若隔离装置规格升级为纯二极管，
作为独立的新传输层 + 协议设计任务立项，不与现有 ISFP 停等链路混用。

## 3. 其他已规划方向（详见 docs/plan.md）

| 方向 | 状态 | 说明 |
|---|---|---|
| V2 快路径（vmagent 双写 remoteWrite） | 已规划 | sender 新增 remote_write 接收端点，e2e 0~1s；写入入口经 vmagent 多目标双写 |
| 稀疏区窗口切片机制（1h 切片） | 可选 | 当前稀疏区封顶 max_window（保守）；移植 influx-sync 切片机制可提升稀疏库回填速率 |
| 租户过滤（accountID/projectID） | 按需 | 有需求时扩展 match 参数即可 |

## 4. 优先级建议

1. **Native 格式**（收益明确、改动集中在 vm 客户端 + 分块 + 测试）；
2. V2 快路径（实时性从轮询级到推送级，改动面较大）；
3. 稀疏区切片（仅当真机稀疏库回填速率不足时）；
4. FEC——不实施（见 §2）。
